# 技術設計 v0.1

## 1. 研究目標

開発対象は古典漢文向けの文字列トークナイザー。主眼は漢文の語彙・機能語・句法を反映した分割の実現であり、単なるトークン数最小化ではない。

## 2. パイプライン

1. **Ingest**: 許可された方法でデータを取得。出典・版・取得日・ライセンス・チェックサムを台帳に記録。
2. **Normalize**: 原文を保持したまま派生データを作成。初期はUnicode NFCのみ。
3. **Deduplicate / Split**: 作品ID・章IDを使って重複を検出し、作品単位で分割。
4. **Baseline**: 文字単位対照群とBPE 16k/32k/64kを作成。
5. **Linguistic analysis**: 否定（不、未、無、非）、判断・断定（也、矣等）、疑問・反語（乎、耶、豈等）、構文パターン（不亦…乎、何…之有等）の分割結果を分析。
6. **Candidate method**: 機能語の保護、候補語彙の優先、語彙スコア補正などを一度に一要素ずつ実験。
7. **Evaluation**: 未見作品に対する圧縮率・速度・復元性・語彙品質を測定。

## 3. 設計原則

- **可逆性**: 正規化を除き、入力テキストの再構成を可能にする。正規化で変わる表記は明示的に記録。
- **原文優先**: 繁体字・異体字・旧字を黙って簡体字に変換しない。
- **句法とトークン境界を混同しない**: 句法候補は分析ラベルとして保持し、文脈依存パターンを固定の一トークンに押し込まない。
- **データの来歴**: 文献単位の出典とライセンスを保存する。異なるライセンスのデータを混ぜる場合は成果物の配布条件を別途評価する。
- **再現性**: コーパスの版・チェックサム・設定・依存関係・乱数条件を記録。
- **比較の公平性**: 同一コーパス、同一分割、同じ語彙サイズ、同一評価器を使う。

## 4. まず比較する方式

A. 文字単位（フォールバック／下限の対照）
B. 標準BPE（16k、32k、64k）
C. 漢文語彙候補を考慮したBPE（将来実装）
D. 機能語・句法候補を分析・保護する方式（将来実装）

v0.1 のCLIはベースラインBPEと基本評価を提供する。C/Dの優位性を前提にせず、結果で採否を決める。

## 5. データ分割と漏洩対策

- 作品・書物単位で train / validation / test を分割。
- 同一作品の異版・章違いが複数splitに跨がないよう、可能な範囲で作品系統IDを使う。
- テストセットは語彙調整や前処理調整に使用しない。
- 近似重複検出の方式と閾値を実験レポートに記載。

## 6. Macでの運用

- Python仮想環境を使用し、依存をロックして再現性を確保。
- 初期はCPUベースのRust `tokenizers` を使用。GPU/ANEを前提にしない。
- 大規模コーパスは外付けSSDに置き、Gitにはコード・設定・メタデータのみを保存。
- LLMを同時ロードせず、メモリ競合を避ける。
- 初回は数MB〜数十MBのデータで動作確認し、実測から規模を拡大。
